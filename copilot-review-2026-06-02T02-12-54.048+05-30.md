# Feature + Implementation Review (omni-crap)

Date: 2026-06-02T02:12:54.048+05:30

This review focuses on **feature correctness** and **implementation reality** (end-to-end data flow, edge cases, contracts), not formatting/style.

## 0) Buildability / shippability (blocking)

- **Does not compile**: `src/regex_engine.rs` initializes `ScopeInfo { … }` but `ScopeInfo` now requires `test_kind: Option<TestKind>` (`src/engine.rs:23-30`). This breaks the regex fallback path entirely.
- `cargo test` reports **0 tests**. There’s no regression net for parsing/scoring/path-mapping behavior.

## 1) Feature claims vs what the code actually does

### “Semantic Complexity (Arborium)… precisely identify functions”

Implementation is *not precise yet*:

- In `TreeSitterEngine::analyze`, the code assumes capture ordering: it treats `m.captures[0]` as the scope node and `m.captures[1]` as the name node.
  - Tree-sitter query matches do **not guarantee** that ordering corresponds to a particular capture name.
  - Result: you can attach the wrong name/range/kind to a scope, which cascades into coverage mapping, diffs, and scores.

- Rust query coverage appears incomplete:
  - The query matches `(function_item …)` and `(impl_item type …)`.
  - It likely **misses methods** in `impl` blocks, so Rust “hotspots” will be systematically under-identified.

### “Coverage Integration… map coverage directly to identified code blocks”

Current implementation makes it likely to report **0 coverage for most blocks** due to path key mismatch:

- `CoverageData::get_function_coverage` keys by `file_path` string (`src/coverage/mod.rs`).
- Parsers store whatever the report contains:
  - lcov `SF:` values are often **absolute paths**.
  - Cobertura filenames vary (relative to module root, package path, etc.).
- The analyzer produces `relative_path` via `strip_prefix(args.path)` (`src/main.rs:274-276`).
- There’s no normalization/relativization step, so keys frequently won’t match → coverage defaults to 0 → risk blows up.

### “Risk Formula” (README) mismatch

README describes:

> `Base Risk = (Complexity² * (1 - Coverage)³) + Complexity` then churn/authors/age.

Code does more than that:

- Adds **Halstead**, **redundancy**, **scatter**, **agent_ratio**, and a “stability factor” plus weight knobs (`calculate_risk` in `src/main.rs`).

This may be fine, but it’s a **contract break**: users can’t interpret scores from the README.

## 2) Scoring model review (implementation-level)

### Structural component

- Structural score roughly averages `complexity` with `halstead/100`, then squares it.
- Halstead in `src/analyzer.rs` is computed as roughly: `leaf_token_count × log2(vocabulary)`.
  - But vocabulary is derived from **all leaf tokens**, so identifiers/literals dominate.
  - This makes the metric sensitive to formatting and renames; you’ll see noisy “risk deltas” from refactors that don’t change behavior.

### Process component

- `agent_signatures` uses substring match for `"bot"` etc. (`src/vcs.rs:51-78`).
  - This will false-positive names like **“Robert”**.
  - The signature `"co-authored-by: *bot"` will never match because `*` is literal.
- Coupling degree uses `count / min_churn` and filters (`count < 5`, `commit_size > 30`).
  - Heuristic might be acceptable, but it’s non-obvious and not configurable; likely overfits by repo size.

## 3) Output/UX correctness

- `--diff` uses git diff outputs and therefore excludes **untracked new files**, even though those are often high-risk changes.
- SARIF metadata looks wrong: `DRIVER_INFO_URI` points to `https://github.com/google/gemini-cli` (`src/sarif.rs`).
  - This is a credibility/traceability problem in CI.

## 4) Architecture issues that block feature growth

- `src/main.rs` is doing too much (CLI + traversal + VCS + scoring + rendering). This makes testing and feature iteration harder.
- There’s no clean library boundary (`lib.rs`), so the core engine/scoring logic can’t be imported and unit-tested easily.
- `forge.rs` isn’t wired in (no `mod forge;`) and references `crate::main::RiskProfile`, which is a design smell for modularity.

## Recommended fix order (turn features into reliable behavior)

1. **Make it compile**: update regex fallback structs and run clippy.
2. **Fix tree-sitter capture selection**: select captures by capture name (e.g., `"func"`, `"class"`, `"name"`) rather than indices.
3. **Improve Rust queries**: include `impl` methods, and ensure function ranges are correct.
4. **Normalize coverage paths**:
   - Convert absolute → relative to `args.path` when possible.
   - Normalize separators.
   - Consider best-effort suffix matching when roots differ.
5. **Align docs vs implementation**: either update README scoring formula to match reality, or simplify scoring to match README.
6. Add minimal tests:
   - Coverage path mapping cases (absolute/relative/mixed separators).
   - Tree-sitter query capture mapping (name before/after scope capture).
